Choose a home by the information's purpose, not just the subject's name. Follow the user's root README and existing collection contracts; the defaults below do not authorize reorganizing an existing Wiki.

| Home           | What belongs here                                                                                               | What does not                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| me.md          | Confirmed profile, durable preferences and cross-context personal constraints                                   | Detailed project status or a copied life history                                                      |
| projects/      | A finite outcome: its scope, decisions, current state and relevant history                                      | General knowledge merely mentioning the project                                                       |
| areas/         | An ongoing responsibility or practice, such as career, health or a hobby                                        | Every activity treated as a separate project                                                          |
| people/        | A person's identity, your relationship and links to shared contexts                                             | Copies of every interaction, application or project involving them                                    |
| organizations/ | An organization's identity, your relationship and links to shared contexts                                      | Copies of employment history, treatment records, application state or product decisions               |
| resources/     | Standalone explanations, methods, guides and reference content useful beyond one particular personal situation | Personal state, decisions, relationships, or company profiles just because they might be useful later |
| daily/         | What happened on a dated day, with evidence and uncertainty                                                     | A second current-state summary or task backlog                                                        |
| sources/       | Retained reports with producer, observation period and original source pointers                                 | Undated conclusions presented as current personal facts                                               |

Examples: “How DPO works” is a resource; “Why we chose DPO for Arden” belongs to the Arden project. A general interview checklist is a resource; one interview's outcome belongs to its application context. A dentist's clinic identity can live in organizations; your treatment belongs with health. A person's role in two projects can be stated once in people, with contextual links from those projects. For example, keep “Jo is my running-club friend; we run Sundays” on Jo's page; the running area links to Jo without copying that relationship or schedule. Cooking as an ongoing practice can be an area; a recipe is a resource; preparing one particular event can be a project.

Before writing, identify the question this note answers and search for its existing owner. Keep each current fact in one primary record; add a meaningful link from another context instead of copying its state. When you fold one page into another, archive it with `merged_into` naming the page that now holds it, so its path keeps opening there; never leave the old path only as an alias. Split genuinely different purposes only when both records are useful on their own. Do not manufacture entity pages for every mention or move project research into resources merely because it could someday be reused.

Start with one readable page per coherent subject. Use sections for related aspects; headings such as “Related”, “Watching” and “Current state” do not by themselves justify child pages. Condense repetition before splitting. Split only for an independently useful reading scope or the actual size limit, and leave a short contextual link in the parent. Do not create empty notes, title-only placeholders, boilerplate page bundles or invented content to fill a directory. Create a directory with its first useful note; its README must explain the actual collection and help readers navigate it.

Prefer shallow paths: one or two directories usually suffice. Add another level only when it groups independently useful records or separates a real producer or workflow. A single subject note does not need its own directory. Name collections for their purpose (for example, career/applications), not a vague entity bucket. These are creation defaults, not permission to move existing pages or flatten useful collections.

Grow navigation alongside useful content. When adding a subject or collection, add a contextual link to the nearest relevant README if it is not already discoverable there. Use `[[path/from/wiki/root.md|readable label]]` for internal navigation and relationships so Memory can resolve links and backlinks; do not use ordinary Markdown links or filesystem-relative `../` paths for other Wiki notes. Describe what a linked note is for; leave its dates, deadlines and status in the owning note. Keep the root README a small entry point into the user's actual contexts; link through collection indexes instead of listing every note. Where a real filing ambiguity arises, a short example linking the user's existing notes can explain the distinction. Do not invent examples, copy mutable status into indexes, rewrite unchanged navigation, or replace the user's filing rules. Useful navigation should emerge during ordinary capture, not depend on a later manual migration.

Keep current summaries distinct from dated evidence and completed history. Keep qualifications, source references and uncertainty; page edit time does not make an old claim current. Cite a chat as a link with its title and the date it was said, `[Mastra application](arden:session/<session_ref>), Sep 30`, never as a raw reference or message number; when the date is unknown, leave it out without saying so. Tasks and automation configuration own executable work. Memory can explain and link a workflow's actual script, inputs and outputs, but does not grant authority to run it. Use inbox/ only when there is durable information whose destination is genuinely unresolved; do not force it into resources. Optional templates/ contains reusable document formats, not empty copies for each subject.
